# Phase 2.5 — Dynamic Tool Search acceptance

Scope: run-scoped catalog selection in `runAgent()` for catalogs larger than 24 tools. The existing core coding tools remain advertised; the remaining local/MCP/runtime tools require bounded search, explicit schema description, and next-turn activation. CLI and Desktop use their existing composition paths without a new authority or provider-specific protocol. Small catalogs retain their full advertised surface.

Safety: hidden-name execution fails closed (including a speculative call in the same response as `tool_describe`); `tool_describe` requires a previously returned search result, validates the whole batch before activation, and cannot grant WRITE/EXECUTE approval. Standard model-order, cancellation, turn/tool-call limits and session/workspace-bound tool execution remain inside `runAgent()`. Catalog state is run-local. Search exposes name/operation/short description, not schemas; full schema enters model context only after explicit description. Extensions must not put secrets in their metadata.

Deterministic coverage: `tests/core/tool-catalog.test.ts` covers pagination through the maximum catalog, MCP-default-size schema activation, same-turn rejection, atomic failures, approval success/denial, cancellation, limits and run isolation. `tests/runtime/tool-catalog-input.test.ts` exercises the actual one-shot CLI and Desktop bridge/runtime tool composition. These use injected models and tools; they do not prove live MCP/provider interoperability, interactive PTY UI, native GUI rendering or platform packages. The catalog rejects >2048 tools or >128-byte names rather than silently omit tools; schemas up to the default MCP 16,384-byte per-tool limit can be described, while larger schemas require host-side correction. Description batches remain bounded to 96,000 bytes and may need to be split into individual calls.

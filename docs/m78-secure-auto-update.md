# M78 — Secure Auto-Update

Status: **IN_PROGRESS — no production updater; not milestone acceptance**.

## Agreed sequence and trust policy

M78 → M79 (Configuration & Migration Lifecycle) → M80 (Production Release Gate).
Each milestone requires tests, completed independent review and acceptance before the next starts. M79/M80 are not started. Publication, tags and releases require separate explicit authorization.

The trust boundary is an Ed25519 signed manifest, not a checksum downloaded alongside an artifact. The manifest binds product, artifact filename, platform, architecture, version, byte length and SHA-256. Production key generation/distribution, OS signing/notarization and production key lifecycle are separate release operations; no such operation is performed here. Public deterministic test keys are fixtures only.

Selected activation policy: platform-native hybrid. macOS applications, Windows installations and Linux AppImage require transactional updates retaining the previous working version. DEB remains owned by the system package manager; in-app DEB activation is explicitly unsupported. A shared managed-slot launcher replacing all existing distribution formats was not selected. Only the AppImage worker primitive is implemented; macOS and Windows adapters and all native acceptance remain to be implemented.

The signed artifact name is now classified fail-closed before any activation work: macOS accepts only `.zip`, Windows only `.exe`, Linux only `.AppImage` as transactional candidates; Linux `.deb` is classified as `external-package-manager`; all other combinations are unsupported. This is an authority-routing guard, not an installer or activation implementation.

## Implemented boundary

`src/desktop/update.ts` supplies verification and private staging primitives, not a working desktop auto-updater. The actual Desktop controller now chains trusted HTTPS transport → private macOS bundle staging → pinned Developer ID verification → conservative target preflight. `openDesktop(runtime, trustedUpdates)` accepts an optional host-injected controller or configuration; default startup remains disabled and discovers no update URLs/keys/paths from environment, workspace or renderer. Parameterless `update_prepare` joins status/check/cancel in the exact-shape bridge. No prepare button is wired yet. No feed, installer, download scheduler or activation path is enabled; `prepared` remains non-installable with `canInstall: false`. No dependency was added.

The controller retains an inert prepared candidate privately until the next operation or close; failed/cancelled/stale results are cleaned before the single-flight lease is released. Close aborts and awaits in-flight native work before removing temporary files, avoiding deletion beneath a late writer. Host-injected native dependencies must honor cancellation or eventually settle; native production commands have their own bounded abort behavior. Hard process termination may leave inert staging; startup scavenging is not implemented. No disposable lifecycle/installer primitive is used. Focused build plus 17 controller, main/shutdown, preparation and transport tests passed, including wrong bundle identity, target and signature, cancellation, deadline, duplicate intent, close cleanup and unchanged active-data sentinel. These fake HTTPS/native tests establish orchestration, not native signed distribution acceptance, installed-app replacement, OS data isolation or milestone closure.

`src/desktop/update-transport.ts` supplies the corresponding unenabled host-composition transport: an explicit credential-free HTTPS manifest URL only, `GET` with redirects rejected and cache disabled, bounded UTF-8 manifest input, verification before the artifact request, then a same-origin artifact URL derived solely from the signed filename. Status, redirect, URL mismatch, cross-origin resolution and declared-length anomalies fail closed. It is injectable for deterministic tests; it neither reads configuration nor enables a feed in desktop startup.

The envelope has exactly `keyId`, `payload`, `signature`. Payload and signature are canonical base64. Ed25519 signs `dragons-agent:update-manifest:v1\n` followed by the exact UTF-8 JSON payload bytes; no JSON reserialization/canonicalization occurs during verification. Key IDs resolve exclusively through the trusted host's pinned public-key map. Keys included in an envelope are rejected. Only Ed25519 keys are accepted. Unknown signers, invalid signatures, unsupported schema, extra fields and malformed/bounded input fail closed.

Payload schema 1 has exactly `schemaVersion`, `product`, `artifact`, `platform`, `arch`, `version`, `size`, `sha256`. Versions currently support stable three-component numeric versions only. The candidate must match the host-selected expected version/artifact/platform/architecture and be strictly newer than the running version. This prevents ordinary downgrade/replay against that version; it is **not** persisted anti-rollback or signed feed freshness protection. A future trusted feed selection policy must not derive its expected target solely from untrusted metadata.

Staging verifies the manifest before consuming any artifact data or creating a candidate. It checks streamed byte count and SHA-256, copies chunks before asynchronous writes, syncs the artifact and stores the signed envelope. On cooperative failure/cancellation the candidate is removed. Cancellation also releases staging when an iterator stalls; transport shutdown remains the host transport's responsibility. Caller supplies the cancellation/deadline signal. Abrupt process/power loss may leave an inert candidate, never a replacement of the active application. There is no extraction or execution.

`src/desktop/update-transaction.ts` supplies a host-owned slot transaction primitive: it acquires an exclusive private lock, writes a durable pending journal before renaming a prepared candidate into the active slot, retains the previous slot, and requires an explicit post-launch health acknowledgement. Startup recovery rolls an unconfirmed candidate back while preserving it as a failed slot; a crash after intent but before replacement retains the current active slot. An existing/stale lock fails closed. Slot/journal names, symlinks and malformed journals fail closed. The primitive does not execute a candidate, access user data, extract an OS installer or integrate with Electron packaging.

`src/desktop/update-appimage.ts` is a Linux-only external-worker primitive for an already-exited AppImage: it re-verifies the staged receipt and bytes before a `COPYFILE_EXCL` candidate copy, runs the slot transaction, then probes only `--dragons-update-health`. `desktop/main.mjs` exits from that mode immediately after Electron readiness and before workspace selection, configuration loading or runtime creation; the health entrypoint accepts both source-Electron and packaged-executable argv forms. `src/desktop/update-health-worker.ts` uses a disposable profile and an allowlisted environment, rejecting unexpected/bounded output, nonzero exit and timeout; a failed probe must complete rollback, otherwise the worker reports a recovery failure rather than suppressing it. This is not an OS sandbox: it relies on the already-verified signed candidate and does not establish M79 real-data compatibility. No desktop updater invokes this worker and no signed source is configured.

The staging root is a trusted-host precondition: a private host-owned directory outside agent workspaces, not writable by untrusted processes. This primitive does not defend against an attacker controlling that root or the same OS account. Staged files are not activation capabilities and must be independently reverified at any future installation boundary. A receipt is not a durable transaction commit or startup-health verdict.

## Rollback/data boundary — mandatory remaining design constraints

Binary rollback alone cannot undo config/session/Memory writes. No M79 compatibility is assumed and no existing user data is migrated or opened by the staging code.

Before activation can ship, implement and test a platform-specific transactional installer/launcher with:

1. Independently verified candidate, immutable previous application, exclusive update ownership, bounded artifact transport and trusted source selection.
2. Durable activation/recovery journal and restart recovery at every irreversible boundary. Incomplete or corrupt state must retain/recover the known-working executable; never launch an unverified leftover candidate.
3. A pre-commit health probe that cannot access real config/session/Memory, credentials or user workspaces. The AppImage worker supplies a disposable-profile, allowlisted-environment probe and main-process early exit; it is not an OS sandbox or real-data migration acceptance.
4. An explicit data-safe policy after commit: do not automatically launch an older binary against data a newer process may have written. Until compatibility is independently established, preserve both binaries/data and fail closed rather than assert automatic rollback is safe.
5. Actual platform installer/relaunch/recovery evidence on the selected macOS arm64, Windows x64 and Linux x64 matrix. Deterministic fixtures establish only their tested boundary, not native installation or power-loss durability.

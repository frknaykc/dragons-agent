# Security Policy

## Shared-session boundary

The shared host is a coordinator above the existing core, not a second executor. It reserves a single foreground owner per session before asynchronous admission, requires revision refresh after another writer, and routes approval/cancellation only to the owning connection. Observer streams omit actionable approval IDs, are independently bounded, and cannot cancel an owner's work when detached. Client IDs do not authenticate callers; trusted host composition and remote principal session access remain required. The optional multi-connection remote mode never relaxes bearer, Origin, Host, sequence or session-ownership checks.

Default file-backed runtimes and persisted interactive CLI runs take an independent exclusive execution lease before loading current continuation, retaining it through execution and persistence. A stale lock is a fail-closed condition, not permission to steal ownership. Injected custom stores without `acquireExecution` do not establish cross-process coordination. Shared revisions cover foreground writes admitted by the shared host, not arbitrary out-of-band edits; the underlying core must not be shared with independent writers.

## Reporting a vulnerability

A private security reporting channel has not yet been established for this repository. Do **not** include API keys, access or refresh tokens, authorization headers, credentials, private project data, or exploit payloads containing sensitive data in a public issue.

Until private reporting is configured, open a minimal public issue that states a security concern exists without disclosing sensitive details. Repository maintainers can later enable GitHub private vulnerability reporting as a repository setting; it is not enabled or assumed by this document.

## Checkpoint concurrency boundary

Session-memory checkpoints cover bounded UTF-8 file creation, deletion and edits inside existing directories after runtime WRITE approval. All selected images and exclusions are inspected before writes; rollback checks the entire selection and reverses only selected receipts. Symlinks, hardlinks, binary images and recognized credential paths/content are excluded. The lexical credential policy is not a complete secret detector. Structural failures retain verified completed receipts, report uncertain paths, and do not adopt external postimages. No structural automatic compensation is attempted.

This is the user-accepted normal development-workspace concurrency boundary, not an atomic hostile-writer guarantee: Node pathname create/unlink and mutable ancestor checks can race an external rename/link/content writer. POSIX structural coverage requires O_NOFOLLOW. On Windows, structural coverage requires the bundled native no-follow handle binding, pinned ancestor checks and exact file IDs; an unavailable binding fails checkpoint mutation closed. Windows read-only leaves are not currently writable/deletable by the native path and must not be reported as restored. Unsupported platforms retain approved legacy writes with explicit no-coverage metadata/warnings, not a checkpoint guarantee. Missing parent directories are rejected. Shell/MCP effects remain outside coverage.

## Review hardening boundaries

- Built-in READ Git operations and automatic change review share `src/read-only-git.ts`: fsmonitor/hooks/signature helpers and optional index writes are disabled; status/diff also disable configured clean/process filters. Diff callers disable external diff and textconv and ignore dirty submodules. Filter discovery failures fail closed. Comparisons use unfiltered worktree bytes; the host still trusts its Git binary and OS, and this is not an arbitrary-command sandbox.
- File writes reject dangling final symlinks. Nested subagent authorization preserves READ without granting delegation/WRITE/EXECUTE. Background start reserves admission before asynchronous persistence and releases claims on failure.
- OpenAI HTTPS endpoint validation includes environment overrides, and its SDK transport rejects redirects. Explicit named-slot selection cannot downgrade to environment credentials or a slot-unaware auth service.
- API-key pools permit 8 named slots per profile/provider, including blocked entries. Named OS records carry version 1 and `ready`/`unverified` state; save verifies both pending and ready writes. Explicit selection can recover a verified ready record after restart. Failed verification/deletion attempts quarantine the entry; a native backend failure can prevent quarantine, so this is not a cross-process atomic transaction. Inventory and bounded cooldown are process-local, listing does not read secrets, and each model instance owns its first-resolution cache. Historical raw/unverified records are not eligible for recovery. API-key storage has no plaintext fallback.
- ChatGPT logout invalidates refresh across load/fetch/save boundaries. Initial native-storage unavailability may select the existing restrictive file fallback; later failures on a usable or selected native backend fail closed rather than downgrading storage.
- Desktop packages include isolated secret-dialog assets; local slash results preserve active-run cancellation identity. Quit remains blocked until cleanup settles, including repeated quit requests. Deterministic tests do not establish installed/native lifecycle acceptance.

## Opt-in language-server boundary (2.1, acceptance pending)

The active profile may explicitly configure one absolute stdio language-server command. Successful built-in file mutations may request a separate `lsp_diagnostics_start` EXECUTE authorization through `runAgent()`. WRITE and session approval never confer future server-start authority. No auto-installation, PATH command discovery, workspace-derived executable selection or inherited credential environment is used. CLI TTY/plain and Desktop approvals display an allowlisted command/ordered-args/document scope, not arbitrary request arguments. The scope is bounded to 4096 serialized UTF-8 bytes; identity-changing redaction, recognized credential flags/values, control/format characters and oversized scopes deny startup before authorization. The Desktop bridge validates this DTO and refuses absent/unsafe LSP scopes. The optional full-screen TUI denies LSP startup because its existing approval surface cannot show the complete scope. `runAgent()` remains the sole startup authority, with one approval per document/process. Each approved document inspection owns an isolated process, bounded framed JSON-RPC stream (one-frame storage, independent of transport chunks) and deadline; server requests are rejected, only exact-document/version diagnostics are consumed, and report text is redacted/bounded before reaching the model or clients.

This is not a process sandbox: an approved server can independently execute project plugins, read or modify files and use the network. Containment applies to documents/URIs supplied and accepted by the client, not arbitrary server behavior. Normal development-workspace concurrency assumptions remain; external writers and mutable ancestors are not atomically excluded. Lexical redaction cannot recognize every secret. POSIX process-group cleanup is best effort for descendants that do not detach; Windows direct-child termination does not guarantee descendant cleanup. Users must trust both server and workspace. See `docs/lsp-diagnostics-acceptance.md` for compatibility and verification limits.

## Relevant security boundaries

- **Programmatic plugins:** manifest discovery reads metadata only, and does not load code. Only a trusted host may supply a plugin factory to `PluginRegistry`; factories execute with host process privileges when a run is composed and are not sandboxed or gated by a later tool approval. Registered plugin tool calls themselves are forced to EXECUTE and pass through `runAgent()` authorization. Unreviewed project/downloaded JavaScript must not be registered merely because its manifest validated. Tool outputs are bounded but may still contain sensitive data supplied by a trusted plugin.
- **Programmatic lifecycle hooks:** trusted hosts bind events to existing tools. Automatic WRITE/EXECUTE actions pass through `runAgent()` authorization for every trigger, without reusing session approval; cancelled runs do not grant durable hook permissions. Event-reported file paths are untrusted hints, not filesystem proof. Hook tool code, like other host-loaded plugin code, is not sandboxed.
- **Reviewed plugin catalog:** SHA-256-pinned manifests are shipped in the package; package-manager hardlinks are accepted only for those digest-checked sources. Installed metadata must remain unlinked and never becomes executable code. Only host-compiled factory code can be explicitly activated and its tool calls remain approval-gated. Install roots must be trusted, single-writer directories: the metadata checks do not guarantee safety against concurrent hostile filesystem swaps.
- **Skills Hub:** pinned, bounded Markdown is advisory context only. Package-manager hardlinks are accepted only for the digest-checked bundled source; installed skills and host-registered sources still reject links. A changed digest invalidates active session references until explicitly reactivated. Host-registered local sources require host trust and single-writer ownership; workspace files cannot register sources automatically.
- **Skill management:** host opt-in tools validate without writing (READ) or require per-call WRITE approval for creation, editing, archiving and deletion. An expected digest prevents stale edits and removals. User skill directory changes are outside workspace checkpoints; no skill text executes merely because it was validated or saved.
- **Skill Curator:** host opt-in, local usage metadata contains scope, IDs, hashes, counts and timestamps, not skill bodies. Suggestions are read-only, never instructions or implicit deletion. State corruption prevents recording, not completion of a previously committed agent turn; host-owned state must be single-writer and free of hostile concurrent filesystem swaps.
- **External Memory contract:** only trusted host adapters can call explicit, one-record share/remove helpers; each call needs a fresh decision for the exact provider, body, scope, and bounded retention. No model-accessible tool, remote adapter, automatic push/pull or persistence of approval is shipped. Lexical secret checks are incomplete, and a real provider's expiry/deletion, backups, scope isolation, transport authentication, and cancellation semantics require separate verification. The network-free fake is test-only, not a service acceptance result.
- **Experimental cron foundation:** host-owned storage contains prompt text, workspace path and skill ID/digest in plaintext app-owned files; lexical credential rejection is incomplete. A trusted host must own the store and model factory. The built-in runner permits only built-in READ tools in one explicit workspace and resolves pinned scope/digest skill context anew each run, refusing changed or unpinned skills; saved tasks never authorize unattended WRITE/EXECUTE. Due slots are reserved before execution (at-most-once attempt, no automatic replay after failure); a process crash may leave an exclusive store lock that needs manual recovery. CLI foreground and Desktop-while-open schedulers exist. Explicit `cron startup install` registers one canonical workspace and profile for next login through a macOS per-user LaunchAgent, Linux systemd user service, or Windows HKCU Run value (no elevation); only macOS/Linux removal stops a loaded service. Windows removal does not stop an already-running process. The registration points to installed Node/CLI paths, so relocation requires reinstalling it; changed Windows entries are not overwritten or removed automatically. No root daemon, automatic registration, or cross-process active-run cancellation exists; real login lifecycle acceptance is still open.
- **Persistent goal lock recovery:** interactive CLI recovery is explicit, profile/workspace-bound and requires a typed confirmation. It reads the lock identity without printing its token, rejects malformed/linked locks, and removes only an unchanged same-host lock whose PID is absent. Process ID reuse and hostile concurrent filesystem swaps are outside this local single-writer guarantee; recovery neither stops an in-flight provider request nor clears a `running` goal reservation.
- **Experimental cross-profile Kanban:** the CLI/Desktop chat/programmatic board is shared across profiles under one trusted base config/workspace and stores plaintext task titles visible to every local profile there. The CLI and Desktop host bind actor identity to the profile loaded at startup; user text and model output cannot select the actor. Profile existence and creator/assignee roles restrict edits. Board data grants no tool approval or automatic worker execution. An exclusive lock and revision checks protect cooperating writers; CLI `/kanban lock status|recover` requires an explicit typed `RECOVER` confirmation; Desktop requires `/kanban lock recover` followed by `/kanban lock confirm RECOVER` within 60 seconds. Both reject live, foreign-host, malformed and changed locks without exposing tokens. Recovery does not cancel another writer; PID reuse and hostile concurrent filesystem swaps remain outside the local guarantee. Host-owned directories and files must not be concurrently replaced by an adversary; this is not an isolation boundary between hostile local OS users.
- **Workspace containment:** built-in file tools validate workspace-relative paths and reject escapes, including unsafe symlink targets.
- **Kanban handoff is not a worker claim:** only the assigned profile can offer an idle task to an existing profile, and only the target profile can accept at the expected revision. An offer blocks progress and dependency edits until accepted or cancelled. A creator can reassign only idle `todo` tasks at 0% progress and clear their offers; this does not stop active work. No process ownership, worker cancellation, session transfer or tool authority is implied by a board handoff.
- **Experimental worker claims:** only trusted programmatic hosts can issue one process-owned claim per idle Kanban task. The board stores SHA-256 of a random token plus host/PID; the raw token is returned only to the caller and omitted from board views. Claimed progress cannot be edited through ordinary board/CLI commands; finalization requires the profile, token, host, PID and expected revision under the board lock. Shared host/PID and digest are not a private process boundary. A crash strands its claim until a trusted host explicitly calls `recoverWorker` with the assigned profile, revision and expected PID. Interactive CLI recovery inspects the claim and requires a separate typed `RECOVER` response; Desktop chat requires a separate, single-use `/kanban worker confirm RECOVER` within 60 seconds after inspection. Recovery refuses a foreign host, live process, stale revision/PID or unverifiable process state; a stopped local process changes the task to `blocked` and invalidates the old token. Recovering `.kanban.lock` does not replay or release a claim. PID reuse, hostile same-user filesystem changes and process death between claim and actual execution are not solved by this reservation. These methods neither launch workers nor authorize tools/model execution.
- **Programmatic Kanban worker lifecycle:** `runKanbanWorker` claims inside its caller's process, waits for the trusted callback to settle, then finishes or blocks the task; no callback result, approval or transcript enters the board. The callback is not sandboxed and must invoke the existing agent authorization boundary, not treat task titles as privileged code. An abort/deadline is cooperative; a non-cooperative callback keeps the claim until it settles or its process dies. Cleanup failure is surfaced without clearing the claim. No automatic retry is provided.
- **Separate Local Kanban worker:** `launchKanbanWorker` starts a fixed, one-shot Node entry with a named, explicitly `local` profile. Only built-in workspace-bounded READ tools are available; no MCP, plugin, hook, WRITE/EXECUTE approval, credential environment or stdout report is inherited. The board title is an untrusted prompt. The local endpoint is chosen by the profile (HTTPS may transmit data externally). Parent cancellation/deadline first signals the child then kills it after a short grace period; a killed child may leave a claim, which requires explicit inspected recovery. This is process separation and bounded cleanup, not a sandbox or cross-platform process-tree containment. CLI and Desktop chat `/kanban worker start <id> <revision>` explicitly launch the child for the startup profile; CLI Ctrl+C or Desktop shutdown cancels it. The Electron parent selects Node mode only for the fixed child process; renderer sandboxing stays enabled. Malformed input and a different assignee cannot claim the task. Neither a board task nor a model response can initiate a launch.
- **Experimental Mixture of Agents:** trusted hosts supply provider/model factories and a READ tool snapshot for `runMixtureOfAgents`; the core does not select providers or authorize data sharing. Interactive CLI `/moa` requires an explicit provider list and `SHARE` confirmation after disclosing profile models and destinations. Desktop chat requires separate `/moa confirm SHARE` within 60 seconds in the same session; it rechecks model selection before sending and aborts on host close. Both production paths use built-in tools, not MCP or session extensions. Every selected provider receives the question and any READ observations it requests; the aggregator receives bounded reports and the question. Candidates have no WRITE/EXECUTE, delegation or inherited continuation, and the aggregator has no tools. Reports remain untrusted text, not instructions or approval, and are not persisted by this flow. Cancellation and deadline require cooperative provider abort and are not an execution sandbox. Model-generated commands cannot invoke `/moa`.
- **Experimental Batch queue:** `createFileBatchQueue` stores bounded, app-scoped prompt/result text, revisions and run reservations; it does not execute models, grant tool permission, or inherit session authorization. Recognized credential shapes are rejected, not exhaustively detected; hosts must not submit secrets or private reports. Each new running task stores process/host identity and a random reservation token; finishing requires its token. A stale reservation remains `running` until an explicit trusted-host decision; no automatic retry is provided. `queue.recover` requires the matching task/revision/token and a verifiably stopped same-host PID, then checkpoints `interrupted` without refunding the run or executing a model. Legacy ownerless reservations cannot be recovered through this path. CLI `/batch recover <id> <revision>` requires explicit `RECOVER`; Desktop requires separate same-session `/batch confirm RECOVER` within 60 seconds and rechecks provider/model selection. Write locks left by a crash require deliberate operator recovery, not age-based removal. `inspectBatchLock` and `recoverAbandonedBatchLock` check bounded lock metadata, an expected token, same-host identity and PID absence; active, foreign, malformed, linked or replaced locks are refused. CLI `/batch lock recover` requires explicit `RECOVER`; Desktop `/batch lock recover` requires a separate same-session `/batch lock confirm RECOVER` within 60 seconds and rechecks provider/model selection. Neither path resumes work. PID reuse and malicious concurrent directory mutation cannot be ruled out by this local filesystem check.
- **Batch execution:** CLI and Desktop chat `/batch` commands select the active profile and canonical workspace, disclose the provider/model and require `RUN` confirmation before execution (Desktop requires a separate same-session `/batch confirm RUN` within 60 seconds). Hosts bind built-in workspace tools only; model/tool extensions cannot invoke the command. Desktop closes by aborting the active run. Trusted programmatic hosts alone can supply the fresh model factory and READ tools to `runBatch`. It discards WRITE/EXECUTE, plan and delegation tools, disables the programmatic tool interpreter, and checkpoints each bounded result. Queue data is workspace-scoped but plaintext; prompt and report checks reject recognizable credential patterns and cannot prove arbitrary text contains no secrets. Do not persist private material in prompts. Failure, cancellation or a crashed process does not automatically rerun a task; inspect an orphaned `running` checkpoint before any operator recovery. This is not a sandbox or an authorization grant to untrusted callers.
- **Authorization:** WRITE and EXECUTE operations fail closed and require explicit Dragons approval. Built-in READ tools are non-mutating by design.
- **Credentials:** Dragons uses native credential storage where supported, with a restrictive local fallback for its own authentication state. Never commit credentials or include them in Memory records.
- **MCP:** configured stdio MCP servers are external local processes. Enable and trust them deliberately; Dragons remains the authorization boundary for their exposed tools.
- **Experimental ChatGPT transport:** the ChatGPT Subscription path is implementation-specific and experimental. Compatibility and security assumptions should be reviewed carefully.
- **API-key login:** Local TUI masked input and a separate ephemeral desktop password dialog send keys only to trusted host credential services. The desktop dialog has its own exact-frame, bounded, one-shot channel and no chat/runtime bridge; the ordinary renderer has no key-submission capability. API keys use profile/provider-namespaced OS storage with verified writes and no plaintext fallback. Cancellation before persistence prevents a write; cancellation cannot roll back a native write already in progress. Remote login is not exposed.
- **Desktop foundation:** local HTML and all model/tool content are untrusted. The renderer is sandboxed with context isolation and no Node integration; exact-main-frame IPC is a validated runtime-command allowlist. Workspace and credentials are host-side only. Packaged local launches require native workspace selection or one explicit absolute `--workspace=` path from the trusted launcher; no renderer or environment workspace override. External navigation/content and renderer permissions are denied. Close/crash/event overflow cancels owned work; approvals are one-use and exact-session/run/request bound. Electron packages are development builds, not signed public or auto-updated distributions.
- **Remote foundation:** the HTTP/SSE server is loopback-only, with host-supplied random bearer credentials per principal, exact Host/Origin policy, bounded input/transport resources, monotonic command sequences and principal-owned session allowlists. Every runtime operation remains behind the validated bridge and `runAgent()` authority. Tokens never authorize direct filesystem/shell RPC. Disconnect cancels owned runs and invalidates pending approvals; reconnect does not replay effects. A separately secured tunnel is required for remote access; no public listener or TLS gateway is shipped. Explicit CORS preflight reveals only fixed protocol metadata, never runtime state.

- **Update verification foundation (M78, incomplete):** artifact trust derives from an Ed25519 signed manifest verified against host-pinned public keys, never a feed-provided key or checksum alone. Verification binds product, artifact, platform, architecture and version to size/SHA-256. Staging requires a private host-owned root outside workspaces. The unconnected Linux AppImage worker re-verifies staged bytes, uses a locked slot transaction and a disposable-profile health probe; it is not an OS sandbox or a real-data migration guarantee. Production updating is disabled; trusted transport, desktop composition, macOS/Windows activation, persisted freshness and data-safe rollback are not implemented or accepted. See `docs/m78-secure-auto-update.md` for the exact boundary and remaining gates.

This policy describes the current project boundaries; it does not guarantee that every third-party provider, MCP server, shell command, or project dependency is safe.

# Security Policy

## Shared-session boundary

The shared host is a coordinator above the existing core, not a second executor. It reserves a single foreground owner per session before asynchronous admission, requires revision refresh after another writer, and routes approval/cancellation only to the owning connection. Observer streams omit actionable approval IDs, are independently bounded, and cannot cancel an owner's work when detached. Client IDs do not authenticate callers; trusted host composition and remote principal session access remain required. The optional multi-connection remote mode never relaxes bearer, Origin, Host, sequence or session-ownership checks.

Default file-backed runtimes and persisted interactive CLI runs take an independent exclusive execution lease before loading current continuation, retaining it through execution and persistence. A stale lock is a fail-closed condition, not permission to steal ownership. Injected custom stores without `acquireExecution` do not establish cross-process coordination. Shared revisions cover foreground writes admitted by the shared host, not arbitrary out-of-band edits; the underlying core must not be shared with independent writers.

## Reporting a vulnerability

A private security reporting channel has not yet been established for this repository. Do **not** include API keys, access or refresh tokens, authorization headers, credentials, private project data, or exploit payloads containing sensitive data in a public issue.

Until private reporting is configured, open a minimal public issue that states a security concern exists without disclosing sensitive details. Repository maintainers can later enable GitHub private vulnerability reporting as a repository setting; it is not enabled or assumed by this document.

## Checkpoint concurrency boundary

Session-memory checkpoints cover bounded UTF-8 file creation, deletion and edits inside existing directories after runtime WRITE approval. All selected images and exclusions are inspected before writes; rollback checks the entire selection and reverses only selected receipts. Symlinks, hardlinks, binary images and recognized credential paths/content are excluded. The lexical credential policy is not a complete secret detector. Structural failures retain verified completed receipts, report uncertain paths, and do not adopt external postimages. No structural automatic compensation is attempted.

This is the user-accepted normal development-workspace concurrency boundary, not an atomic hostile-writer guarantee: Node pathname create/unlink and mutable ancestor checks can race an external rename/link/content writer. O_NOFOLLOW is required for structural coverage; unsupported platforms retain approved legacy writes with explicit no-coverage metadata/warnings, not a checkpoint guarantee. Missing parent directories are rejected. Shell/MCP effects remain outside coverage.

## Review hardening boundaries

- Built-in READ Git operations and automatic change review share `src/read-only-git.ts`: fsmonitor/hooks/signature helpers and optional index writes are disabled; status/diff also disable configured clean/process filters. Diff callers disable external diff and textconv and ignore dirty submodules. Filter discovery failures fail closed. Comparisons use unfiltered worktree bytes; the host still trusts its Git binary and OS, and this is not an arbitrary-command sandbox.
- File writes reject dangling final symlinks. Nested subagent authorization preserves READ without granting delegation/WRITE/EXECUTE. Background start reserves admission before asynchronous persistence and releases claims on failure.
- OpenAI HTTPS endpoint validation includes environment overrides, and its SDK transport rejects redirects. Explicit named-slot selection cannot downgrade to environment credentials or a slot-unaware auth service.
- API-key pools permit 8 named slots per profile/provider, including blocked entries. Named OS records carry version 1 and `ready`/`unverified` state; save verifies both pending and ready writes. Explicit selection can recover a verified ready record after restart. Failed verification/deletion attempts quarantine the entry; a native backend failure can prevent quarantine, so this is not a cross-process atomic transaction. Inventory and bounded cooldown are process-local, listing does not read secrets, and each model instance owns its first-resolution cache. Historical raw/unverified records are not eligible for recovery. API-key storage has no plaintext fallback.
- ChatGPT logout invalidates refresh across load/fetch/save boundaries. Initial native-storage unavailability may select the existing restrictive file fallback; later failures on a usable or selected native backend fail closed rather than downgrading storage.
- Desktop packages include isolated secret-dialog assets; local slash results preserve active-run cancellation identity. Quit remains blocked until cleanup settles, including repeated quit requests. Deterministic tests do not establish installed/native lifecycle acceptance.

## Opt-in language-server boundary (2.1, acceptance pending)

The active profile may explicitly configure one absolute stdio language-server command. Successful built-in file mutations may request a separate `lsp_diagnostics_start` EXECUTE authorization through `runAgent()`. WRITE and session approval never confer future server-start authority. No auto-installation, PATH command discovery, workspace-derived executable selection or inherited credential environment is used. CLI TTY/plain and Desktop approvals display an allowlisted command/ordered-args/document scope, not arbitrary request arguments. The scope is bounded to 4096 serialized UTF-8 bytes; identity-changing redaction, recognized credential flags/values, control/format characters and oversized scopes deny startup before authorization. The Desktop bridge validates this DTO and refuses absent/unsafe LSP scopes. The optional full-screen TUI denies LSP startup because its existing approval surface cannot show the complete scope. `runAgent()` remains the sole startup authority, with one approval per document/process. Each approved document inspection owns an isolated process, bounded framed JSON-RPC stream (one-frame storage, independent of transport chunks) and deadline; server requests are rejected, only exact-document/version diagnostics are consumed, and report text is redacted/bounded before reaching the model or clients.

This is not a process sandbox: an approved server can independently execute project plugins, read or modify files and use the network. Containment applies to documents/URIs supplied and accepted by the client, not arbitrary server behavior. Normal development-workspace concurrency assumptions remain; external writers and mutable ancestors are not atomically excluded. Lexical redaction cannot recognize every secret. POSIX process-group cleanup is best effort for descendants that do not detach; Windows direct-child termination does not guarantee descendant cleanup. Users must trust both server and workspace. See `docs/lsp-diagnostics-acceptance.md` for compatibility and verification limits.

## Relevant security boundaries

- **Workspace containment:** built-in file tools validate workspace-relative paths and reject escapes, including unsafe symlink targets.
- **Authorization:** WRITE and EXECUTE operations fail closed and require explicit Dragons approval. Built-in READ tools are non-mutating by design.
- **Credentials:** Dragons uses native credential storage where supported, with a restrictive local fallback for its own authentication state. Never commit credentials or include them in Memory records.
- **MCP:** configured stdio MCP servers are external local processes. Enable and trust them deliberately; Dragons remains the authorization boundary for their exposed tools.
- **Experimental ChatGPT transport:** the ChatGPT Subscription path is implementation-specific and experimental. Compatibility and security assumptions should be reviewed carefully.
- **API-key login:** Local TUI masked input and a separate ephemeral desktop password dialog send keys only to trusted host credential services. The desktop dialog has its own exact-frame, bounded, one-shot channel and no chat/runtime bridge; the ordinary renderer has no key-submission capability. API keys use profile/provider-namespaced OS storage with verified writes and no plaintext fallback. Cancellation before persistence prevents a write; cancellation cannot roll back a native write already in progress. Remote login is not exposed.
- **Desktop foundation:** local HTML and all model/tool content are untrusted. The renderer is sandboxed with context isolation and no Node integration; exact-main-frame IPC is a validated runtime-command allowlist. Workspace and credentials are host-side only. External navigation/content and renderer permissions are denied. Close/crash/event overflow cancels owned work; approvals are one-use and exact-session/run/request bound. Electron is a development-only shell, not an installed or auto-updated desktop distribution.
- **Remote foundation:** the HTTP/SSE server is loopback-only, with host-supplied random bearer credentials per principal, exact Host/Origin policy, bounded input/transport resources, monotonic command sequences and principal-owned session allowlists. Every runtime operation remains behind the validated bridge and `runAgent()` authority. Tokens never authorize direct filesystem/shell RPC. Disconnect cancels owned runs and invalidates pending approvals; reconnect does not replay effects. A separately secured tunnel is required for remote access; no public listener or TLS gateway is shipped. Explicit CORS preflight reveals only fixed protocol metadata, never runtime state.

- **Update verification foundation (M78, incomplete):** artifact trust derives from an Ed25519 signed manifest verified against host-pinned public keys, never a feed-provided key or checksum alone. Verification binds product, artifact, platform, architecture and version to size/SHA-256. Staging requires a private host-owned root outside workspaces. The unconnected Linux AppImage worker re-verifies staged bytes, uses a locked slot transaction and a disposable-profile health probe; it is not an OS sandbox or a real-data migration guarantee. Production updating is disabled; trusted transport, desktop composition, macOS/Windows activation, persisted freshness and data-safe rollback are not implemented or accepted. See `docs/m78-secure-auto-update.md` for the exact boundary and remaining gates.

This policy describes the current project boundaries; it does not guarantee that every third-party provider, MCP server, shell command, or project dependency is safe.
